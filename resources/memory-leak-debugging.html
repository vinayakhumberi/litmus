1. Heap Memory Basics — What You're Actually Looking At

Every value in JavaScript lives in one of two places. The stack holds primitives and function call frames — fixed-size, LIFO, cleaned up automatically the instant a frame pops. The heap is a large, unstructured region where every object, array, function, and closure actually lives; it is cleaned up only by the garbage collector, never by a variable simply going out of scope. (For an animated, step-by-step version of this split — including exactly what a closure keeps alive and why — see the JS Memory & Execution Visualizer. Everything below builds on that.)

V8 (Chrome and Node's engine) doesn't treat the heap as one flat blob — it's split into generations, because of the generational hypothesis: the overwhelming majority of objects die young (a render's temporary props object, one iteration's loop variable), so the collector is optimized hard for cheaply reclaiming short-lived garbage, and only occasionally pays for a full, more expensive sweep of what's left.

New Space (Young Generation)

Small (a few MB), where every new object is allocated first. Split into two semi-spaces; a fast, frequent Scavenge (minor GC) copies survivors from one to the other. Objects that survive a couple of scavenges get promoted to Old Space.

Old Space (Old Generation)

Where promoted, long-lived objects go. Cleaned by a slower, less frequent Mark-Sweep-Compact ("Major GC") — the pass that causes visible jank if it runs on the main thread, and what a heap snapshot is mostly showing you.

Large Object Space

Objects too big to fit comfortably in New Space (large arrays, big strings) are allocated here directly, regardless of age.

Code / Map Space

Compiled function code and "hidden class" shape metadata. Rarely the target of a leak hunt, but shows up as its own category in a snapshot.

The only question the collector ever asks is reachability, not lifetime or usage. Starting from a set of GC roots (the global object, everything currently on the call stack, active closures), the collector walks every reference it can find; anything reachable through that walk is kept alive — unconditionally, no matter what your program logic thinks — and anything it can't reach gets swept. (This is the exact mark-and-sweep process animated in the visualizer's GC example, if you want to watch it happen step by step.)

So what is a "memory leak" in a garbage-collected language? You never manually free anything in JS, so a leak here specifically means: an object your program logic considers dead is still reachable from a root through some reference you forgot you were holding — an unremoved event listener, a stale closure, a cache with no eviction, an uncleared timer. The garbage collector is doing its job correctly the whole time; the bug is upstream, in code that's still (accidentally) pointing at the object.

Two numbers appear on every row of a heap snapshot, and reading them correctly is the actual skill:

TermMeaning
Shallow sizeMemory the object itself occupies — not counting anything it points to.
Retained sizeMemory that would be freed if this object became unreachable, including everything only reachable through it. This is the number that actually matters when hunting leaks — a tiny object with a huge retained size is usually the head of the leak, not the small object itself.
Retainers / Retaining pathFor any object, DevTools can show the chain of "what's holding onto this," back up to a GC root. Reading that chain is how you go from "this object leaked" to "this specific line of code is why."

2. Why no screenshots (and how to use this)

A static screenshot of DevTools would go stale the moment Chrome ships a UI update, and worse, it can't actually teach you anything you can't already read in the docs. Every scenario below genuinely leaks or doesn't depending on a toggle — the same real JavaScript objects, DOM nodes, and closures described in the write-up, running live in your own browser. Open Chrome DevTools now (F12 or Cmd+Opt+I) and follow along with your own Memory panel — that's the actual skill being taught here.

The three-snapshot technique, applied to every scenario below:
  1. DevTools → Memory tab → select Heap snapshot → click Take snapshot (this is your baseline).
  2. Perform the scenario's "leak" action a few times using the buttons below.
  3. Click the Collect garbage button in the Memory panel's toolbar (a small circular icon), then take a second snapshot.
  4. Perform the same action again, collect garbage again, take a third snapshot.
  5. Select the third snapshot, change the view dropdown from Summary to Comparison, and set the baseline to the second snapshot.
  6. Sort by Size Delta or # New — this isolates objects that grew across both intervals, which is what a real leak looks like versus incidental retained state.
Honest caveat: exact panel names/icons can shift slightly between Chrome versions. The mechanism (heap snapshot → comparison view → retainer tree) has been stable for years and is what to focus on, not the precise pixel layout.

3. Scenario: Forgotten setInterval

Each "mount" creates a widget holding a ~50,000-element array, plus a setInterval whose closure references that array. In buggy mode, "Unmount all" only removes our own reference to the widgets — the browser's timer system still holds the interval callback (and everything it closed over) alive, because an uncleared interval is retained by the runtime itself, independent of any variable in your code.

Widgets currently tracked by us: 0
Intervals actually still running: 0
A. Confirm the leak (fix OFF)
  1. Make sure Apply the fix above is unchecked.
  2. Open DevTools (F12 / Cmd+Opt+I) → Memory tab → select Heap snapshot → click Take snapshot. This is your baseline.
  3. Back on the page, click Mount 20 widgets three times (60 total), then click Unmount all. Watch "Widgets currently tracked by us" drop to 0 — don't trust that number yet.
  4. In the Memory panel's toolbar, click the small circular Collect garbage icon, then click Take snapshot again (snapshot #2).
  5. Repeat step 3 once more (mount 60, unmount all), click Collect garbage again, take a third snapshot.
  6. Select snapshot #3, change the view dropdown from Summary to Comparison, and set the comparison baseline to snapshot #2.
  7. Click the # Delta column header to sort by it. Look for: an Array row with a positive, growing delta even though you "unmounted" everything both times — each retained widget's 50,000-element array is still alive. (Exactly how V8 labels the closure/context object itself varies by Chrome version — it won't reliably say "closure," so Array is the filter to trust here.) Click that Array row, expand Retainers below it, and confirm the chain leads back to a timer entry rather than to trackedWidgets.
B. Confirm the fix (fix ON)
  1. Check Apply the fix.
  2. Repeat the exact same mount → unmount → collect garbage → snapshot cycle from steps 2–6 above.
  3. Compare: the same Array row in the Comparison view should now sit at roughly 0 delta — clearInterval on unmount actually releases them this time.

🔎 Deduction: what the evidence means, and where to look in real code

What it means: a growing Array delta that survives repeated "unmount + collect garbage" cycles, with a Retainers chain that leads to a timer instead of any variable in your own tracking code, means something is still ticking for objects your app already considers gone. In a GC'd language, a timer that's still armed is a first-class reason an object can't die — no user-facing symptom (a component visually disappearing) tells you whether its setInterval/setTimeout died with it.

Where to look in your own codebase:

  • Grep for every setInterval( and setTimeout( call site, then check each one has a matching clearInterval / clearTimeout reachable from wherever that component/module actually tears down: 
    grep -rn "setInterval(\|setTimeout(" src/
  • For each hit, ask: is the interval/timeout ID stored somewhere the teardown code can actually reach it? A common bug is storing the ID on a local variable that goes out of scope, instead of on the component instance/ref.
  • In React: is the setInterval started inside useEffect, and does that same useEffect return a cleanup function that calls clearInterval? A useEffect with no return value is the single most common source of this exact leak.
  • Check every early-return / conditional branch in the unmount or cleanup path — a cleanup function that only calls clearInterval inside an if that doesn't always fire will leak intermittently, which is much harder to catch by inspection than by testing with the three-snapshot technique above.
  • Don't forget third-party libraries: a polling widget, an analytics SDK, or a "keep-alive" heartbeat can start its own internal interval you never call directly — check its docs for a destroy()/dispose() method and confirm your code actually calls it on unmount.

4. Scenario: Detached DOM Node via Uncleaned Listener

Each "mount" appends a padded DOM subtree to the page and registers a window resize listener whose closure references that subtree. Removing the panel from the document (what "Unmount" does) does not make it collectible if the listener is never removed — window outlives the panel and keeps the listener, and the listener keeps the node.

Panel currently in the document: no
Resize listeners registered: 0
A. Confirm the leak (fix OFF)
  1. Make sure Apply the fix above is unchecked.
  2. Click Mount a panel.
  3. Click Unmount the panel. The stat badge "Panel currently in the document" flips to "no" — that only proves it left the DOM tree, not that it's collectible.
  4. DevTools → Memory tab → Heap snapshot → Take snapshot.
  5. In the snapshot results, find the class filter search box near the top of the list and type Detached into it.
  6. Look for: a group called Detached <div>, expandable to a row reading Detached <div class="leak-panel"> — that's this scenario's panel, confirmed still in memory by its own class name. Click that row, then expand Retainers in the panel at the bottom of the DevTools window — walk the chain until you find the resize listener on window as the thing still holding it, exactly as described above.
B. Confirm the fix (fix ON)
  1. Check Apply the fix.
  2. Click Mount a panel, then Unmount the panel again.
  3. Take a fresh heap snapshot and search Detached again. Compare: this time the filter should return nothing new — removeEventListener on unmount let the node go.

🔎 Deduction: what the evidence means, and where to look in real code

What it means: a row under the Detached filter is unambiguous — it's a DOM node no longer in the visible page, kept alive purely by a JS reference. The Retainers chain telling you it's a listener on window (or document) specifically is the key detail: those two targets outlive almost everything else on the page, so any listener registered on them and never removed is a leak by construction, not just a possibility.

Where to look in your own codebase:

  • Grep for listeners attached to long-lived targets specifically — these are far more dangerous than listeners on a component's own DOM node: 
    grep -rn "window.addEventListener\|document.addEventListener" src/
  • For each hit, confirm a matching removeEventListener exists on the teardown path — and that it passes the exact same function reference. removeEventListener('resize', () => {...}) with a freshly-written inline arrow function does nothing; it silently fails because it's not the same function object that was added. This is one of the most common "I did clean up, but it still leaks" bugs.
  • In React: check useEffect hooks that call window.addEventListener or document.addEventListener — the cleanup function returned from that useEffect must call removeEventListener with the identical handler reference, usually meaning the handler needs to be defined once (e.g. via useCallback or declared outside the effect body) rather than inline.
  • Check any code that removes a DOM node directly (el.remove(), parentNode.removeChild(el), or a framework unmounting it) without first checking whether that node — or anything inside it — had listeners registered on a global target.
  • Third-party widgets (modals, tooltips, drag-and-drop libraries) are a frequent source here too — check their docs for a destroy() call and confirm it's actually invoked when your component using them unmounts.

5. Scenario: Unbounded Map Cache vs. WeakMap

Each "view a user" call creates a DOM node standing in for a user card and a ~10,000-element array standing in for cached summary data, then caches them keyed by the node. The node is never appended anywhere and nothing else references it after the function returns — whether it's collectible depends entirely on which cache holds it.

Regular Map size: 0
WeakMap size: not inspectable — that's the point
A. Confirm the leak (fix OFF — regular Map)
  1. Make sure Use WeakMap instead of Map is unchecked, and click Reset caches first to start clean.
  2. DevTools → Memory tab → Heap snapshot → Take snapshot (baseline).
  3. Click View 20 users three times (60 total). Watch "Regular Map size" climb to 60.
  4. Click Collect garbage, then take snapshot #2.
  5. Click View 20 users once more (20 more), collect garbage again, take snapshot #3.
  6. Select snapshot #3 → Comparison view → baseline = snapshot #2 → sort by # Delta.
  7. Look for: an Array row with a delta matching the 20 new entries (exact grouping/naming of the surrounding object rows can vary slightly by Chrome version), surviving every garbage collection — the regular Map is a strong reference keyed by a node nothing else points to, so GC can never touch it.
B. Confirm the fix (fix ON — WeakMap)
  1. Check Use WeakMap instead of Map, then click Reset caches.
  2. Repeat the exact same click / collect-garbage / snapshot cycle from steps 2–5 above.
  3. Compare: the Array delta in the Comparison view should now sit at roughly 0 — each user-card node becomes unreachable the instant viewUsers returns, since a WeakMap never counts as a strong reference.
  4. Note that "WeakMap size" deliberately can't show a live count in the UI — that's the whole point of a WeakMap being non-enumerable. The heap snapshot comparison is the only way to verify it's actually being cleaned up.

🔎 Deduction: what the evidence means, and where to look in real code

What it means: an Array/object-count delta that climbs in lockstep with how many times you called the "view" action, and never drops after a garbage collection, points at a cache or lookup table that's a strong reference with no eviction — not a timer, not a listener, just a data structure that only ever grows.

Where to look in your own codebase:

  • Grep for module-level or long-lived caches — these are the ones that outlive any individual request/render and are the most common offenders: 
    grep -rn "new Map(\|new WeakMap(\|= {}" src/ | grep -i "cache\|registry\|store"
  • For each cache you find, ask two questions: (1) is it keyed by an object/DOM node/instance that should become garbage once its "owner" is gone? If yes, a plain Map or object is the wrong tool — it should be a WeakMap (or WeakSet if you only need presence, not a value). (2) If it's legitimately keyed by a primitive (a string ID, a URL) — where WeakMap isn't an option, since WeakMap keys must be objects — does it have any eviction policy (max size, TTL, LRU)? An unbounded primitive-keyed cache is a leak by a different name.
  • Check "memoize" utility functions and library-provided caching layers (data-fetching libraries, computed-value memoizers) for a documented cache size limit — many default to unbounded unless configured otherwise.
  • Search for anywhere a DOM node, component instance, or callback is used as an object key at all — that's the single strongest signal this scenario applies: 
    grep -rn "\.set(\(node\|el\|element\|ref\|instance\)" src/

6. Scenario: The Dynamic-Key Global Leak

This is the JSONP-callback / debug-leftover pattern: instead of overwriting one shared identifier, each call stashes a ~20,000-element array under a freshly generated property name directly on window — the pattern real code hits when it does window['handler_' + requestId] = fn for a dynamic callback, or leaves window['debugSnapshot_' + n] = hugeObject in for "just this once." Because window is a GC root, every one of those keys is reachable forever — nothing ever needs to reference them again for them to survive.

Leaked keys on window: 0
Entries in local Map: 0
A. Confirm the leak (fix OFF)
  1. Make sure Apply the fix above is unchecked.
  2. Open the DevTools Console tab (not Memory this time) and run: Object.keys(window).filter(k => k.startsWith('handler_')).length. Note the number.
  3. Back on the page, click Run 20 'dynamic callback' registrations.
  4. Re-run the exact same console line. Compare: the count jumped by 20.
  5. Click Clear (simulate proper cleanup), then re-run the console line a third time. Look for: the count is unchanged — "Clear" did nothing for the buggy path, because nothing in the code ever deletes those window keys.
  6. Optional, to see it in a snapshot too: Memory tab → take a snapshot → Comparison against an earlier baseline — the Array class delta will match the leaked-key count exactly.
B. Confirm the fix (fix ON)
  1. Check Apply the fix.
  2. Click Run 20 'dynamic callback' registrations. Watch "Entries in local Map" climb to 20 while "Leaked keys on window" stays flat.
  3. Click Clear (simulate proper cleanup). Compare: "Entries in local Map" drops back to 0.
  4. Re-run the console line from step 2 above to confirm no new window.handler_* keys were ever created in fixed mode.

🔎 Deduction: what the evidence means, and where to look in real code

What it means: if Object.keys(window) (or globalThis) shows a count that only ever grows, no cache-clearing function in your app can be trusted to touch it — by definition, nothing is watching those keys or deciding when they're done. This is the one leak type you can confirm without opening the Memory panel at all.

Where to look in your own codebase:

  • Grep for any code writing to window or globalThis with a computed/dynamic property name — the bracket syntax is the tell, a hardcoded key like window.myGlobal can't accumulate the way a dynamic one can: 
    grep -rn "window\[\|globalThis\[" src/
  • Classic sources: a JSONP-style callback registered as window['callback_' + requestId], a per-widget or per-iframe handle stashed on window for cross-script access, or debug/telemetry code that does window['__debug_' + Date.now()] = someObject and was never meant to ship.
  • Also grep for accidental implicit globals — a plain assignment with no let/const/var inside a non-strict-mode function creates one silently: 
    grep -rn "^\s*[a-zA-Z_$][a-zA-Z0-9_$]* = " src/ | grep -v "let \|const \|var \|\."
    (noisy — treat it as a starting point, not a precise match; a linter rule like ESLint's no-implicit-globals/no-undef catches this far more reliably going forward.)
  • If you find a legitimate reason to expose something dynamically on window, replace it with a module-scoped Map you control (as the fix above does) — you get the same dynamic-key lookup with an actual place to call .delete() or .clear() from.

7. Scenario: The Never-Unsubscribed Event Bus

A minimal pub/sub bus (the same shape as Node's EventEmitter or any custom app-wide event bus) keeps an array of subscriber callbacks. Each "component" subscribes with a callback that closes over a ~30,000-element buffer meant to represent per-component state. If "unmounting" the component never calls the matching unsubscribe, the bus's listener array — and everything each closure captured — stays reachable forever, because the bus itself is a long-lived, module-scoped object that's always a GC root's descendant.

Components we think are mounted: 0
Listeners actually still on the bus: 0
A. Confirm the leak (fix OFF)
  1. Reload this page first (this scenario's bus persists across runs — reloading guarantees a clean count). Make sure Apply the fix is unchecked.
  2. Open the DevTools Console tab so you can see logged output.
  3. Click Mount 15 subscriber components. Note "Listeners actually still on the bus" = 15.
  4. Click Unmount all. "Components we think are mounted" drops to 0 — but look for: "Listeners actually still on the bus" staying at 15. That mismatch is the leak.
  5. Click Emit an event (proves they're still live). Look at the console: all 15 "[component N] still subscribed..." lines print, even though you just "unmounted" every one of them — the bus's own listeners array, not your tracking array, is what's keeping every closure (and its 30,000-item buffer) alive. This is exactly the shape of a real MaxListenersExceededWarning in Node, or a React app that subscribes to a global event bus in useEffect with no cleanup function returned.
B. Confirm the fix (fix ON)
  1. Reload the page again for a clean count, then check Apply the fix.
  2. Click Mount 15 subscriber components — "Listeners actually still on the bus" reads 15.
  3. Click Unmount all. Compare: this time "Listeners actually still on the bus" drops back to 0, since each subscriber now calls its own unsubscribe().
  4. Click Emit an event again — the console stays silent, confirming those components are actually gone from the bus, not just from your own tracking array.

🔎 Deduction: what the evidence means, and where to look in real code

What it means: a listener count on a shared bus/emitter that keeps climbing (or a Node MaxListenersExceededWarning in your real logs) while your own "how many components are mounted" count goes back to 0 means the emitter — not your component tree — is the actual owner of those closures. Every subscriber that never unsubscribed, plus everything it captured, is retained for the lifetime of the bus, which is usually the lifetime of the whole app.

Where to look in your own codebase:

  • Grep for every subscription call against a shared/singleton emitter — .on(, .addListener(, and .subscribe( are the three spellings to check: 
    grep -rn "\.on(\|\.addListener(\|\.subscribe(" src/
  • For each hit, find the matching teardown call (.off(, .removeListener(, or the object returned by .subscribe( usually exposes an .unsubscribe()) and confirm it's actually invoked on the same lifecycle event as the subscription — not just defined somewhere and never called.
  • In React: check every useEffect that subscribes to a global bus, a Redux store, or an event emitter — if the effect doesn't return () => bus.off(handler) (or equivalent), every remount adds a new listener that never goes away, and the app leaks a little more on every navigation.
  • In Node specifically, treat any real MaxListenersExceededWarning in your logs as exactly this scenario playing out live — it's Node's own built-in leak detector for EventEmitter, and the fix is always "find the subscribe call whose matching unsubscribe never runs."
  • Be suspicious of any handler defined as an inline arrow function passed directly into .on(...) — the same reference problem as in Scenario 4's listener leak applies here too: you can't unsubscribe a handler you never kept a reference to.

8. Detection Toolkit: Beyond Heap Snapshots

The three-snapshot technique above is the core skill, but it's not the only tool — and for a quick first check, it's often not even the fastest one. Use these on the scenarios above to build a fuller picture of what each one confirms.

Performance Monitor — a 10-second smoke test

This is a different panel from the "Performance" tab you may already know — there's no Start/Stop recording here. It's a live dashboard of line graphs that update continuously while you use the page, useful as a quick first check before reaching for a full heap snapshot.

  1. With DevTools open, press Cmd+Shift+P (Mac) or Ctrl+Shift+P (Windows/Linux). This opens DevTools' Command Menu — a searchable command palette, separate from anything on the page itself.
  2. Type performance monitor and select Show Performance Monitor. A new panel opens with live graphs already running: JS heap size, DOM Nodes, JS event listeners, Documents, and a few others.
  3. Go back to a scenario above and click its "leak" and "cleanup" buttons repeatedly (e.g. Mount / Unmount, several times in a row) while watching the graphs move in real time.
  4. Look for: the JS heap size line tracing a "sawtooth" shape — climbing as things allocate, then dropping sharply whenever a garbage collection runs. That shape by itself is healthy. The leak signal is the floor of each drop: if it settles back to roughly the same baseline every time, you're fine; if it creeps a little higher after every cycle and never comes back down, that rising floor is your first hard evidence of a leak.
  5. Compare the DOM Nodes and JS event listeners lines against JS heap size at the same time: if those climb too, you're looking at a DOM leak (like Scenario 4, the detached-panel one); if only heap size climbs while DOM Nodes/Listeners stay flat, it's a pure JS data-structure leak (like Scenarios 6 and 7 above).

Allocation instrumentation on timeline

Memory tab → select Allocation instrumentation on timeline → Start. Perform a scenario's leak action several times over a few seconds, then Stop. Each vertical bar represents allocations in that time slice; blue bars are objects still alive, grey bars are ones already collected. Click a tall blue bar that recurs on every action-repeat — this isolates just the objects allocated in that narrow window, filtering out unrelated page noise, and is often faster than the full three-snapshot comparison for confirming "yes, this specific action is what's allocating the retained objects."

Console-only utilities (these don't exist in regular page JavaScript)

UtilityWhat it's for
getEventListeners(node)Lists every listener attached to a specific DOM node, grouped by event type. Run against the panel element in Scenario 4 (the detached-listener one) before and after "Unmount" to directly confirm whether the resize listener is actually gone — no snapshot needed.
queryObjects(Ctor)Returns every live instance of a given constructor currently on the heap. Expose a class via window.MyClass = MyClass so the console can reach it, then run queryObjects(MyClass) — a growing count across repeated mount/unmount cycles is a leak, confirmed directly, with no snapshot comparison at all.
performance.memory.usedJSHeapSizeChrome-only, approximate (rounded for security reasons), but pollable: wrap it in a setInterval + console.log for a crude, no-panel-needed heap graph while a scenario runs.

All three only work typed directly into the DevTools console on the inspected page — they're console-utility globals injected by DevTools itself, not real JS APIs, so they'll throw ReferenceError if called from a script tag.

Reading a retainer chain to find the actual line of code

In a Comparison snapshot, click a suspicious row → expand Retainers in the bottom pane. The chain shown is "what's holding this object alive," read from your object back up toward a GC root. Walk it top-to-bottom; the first entry that's recognizably your code — a named closure, a variable from one of the scenarios above, a listener callback — rather than an internal engine structure, is almost always the exact place to go fix.

Chrome's dedicated Detached Elements panel

Newer Chrome versions ship DevTools → More tools → Detached elements — a one-click alternative to manually filtering a heap snapshot for the word "Detached" the way Scenario 4 (the uncleaned-listener DOM panel) above describes. If it's available in your Chrome version, it lists every currently-detached subtree and its retaining path directly, skipping the manual snapshot filter step entirely.
