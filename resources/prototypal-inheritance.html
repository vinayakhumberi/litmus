1. The Mental Model, Before Any Spec Terms

Every object in JavaScript can have exactly one other object marked as "ask this one if you can't find what you're looking for." When you read obj.prop and obj doesn't have prop itself, the engine doesn't fail immediately — it asks that linked object. If that object doesn't have it either, it asks whatever it's linked to, and so on, until either something answers or there's nothing left to ask.

That's the entire mechanism — a chain of objects, each one delegating a lookup to the next when it comes up empty. Nothing is copied; the chain is walked fresh at the moment you access the property, not decided in advance.

A concrete trace — nothing here is ever copied, only linked:

const base = { greet() { return 'hi'; } };
const derived = Object.create(base); // derived.[[Prototype]] is now base

derived.greet();
// 1. Does derived have its own 'greet'? No.
// 2. Follow derived.[[Prototype]] to base. Does base have 'greet'? Yes.
// 3. Call it, with `this` still bound to derived — returns 'hi'.

base.greet = function () { return 'hello'; }; // mutate base AFTER the link already exists
derived.greet(); // 'hello' — the link is just followed again, nothing was "baked in" earlier

2. Chain Walker — Look Up a Property Live

This mirrors Scenario 4 from the deep-dive: rex is linked to Dog, which is linked to Animal, which is linked to Object.prototype. Pick a property below and watch the engine walk the chain one link at a time.

const Animal = {
  init(name) { this.name = name; return this; },
  speak() { return `${this.name} makes a sound`; },
};
const Dog = Object.create(Animal);              // Dog.[[Prototype]] is Animal
Dog.speak = function () { return `${this.name} barks`; }; // override, shadows Animal's speak

const rex = Object.create(Dog).init('Rex');     // rex.[[Prototype]] is Dog

Implementing it directly makes the four steps concrete:

function myNew(Constructor, ...args) {
  const instance = Object.create(Constructor.prototype); // link [[Prototype]]
  const result = Constructor.apply(instance, args);       // run constructor, this = instance
  return (typeof result === 'object' && result !== null) ? result : instance;
  // typeof null === 'object' is why the null check is required, not just typeof
}

5. Why the Engine Cares About Object "Shape"

Walking a chain of links on every property access would be slow if engines actually did it fresh every time. In practice, V8 optimizes around one observation: objects created the same way usually end up with the same properties in the same order — a repeated layout called a hidden class ("shape"). Once seen before, the engine skips straight to the right memory offset via an inline cache instead of re-walking the chain.

Code that reliably hits this fast path is monomorphic; code where the same call site keeps seeing different shapes degrades toward megamorphic — the slow end.

6. Composition Over Inheritance: React's Own Proof

Deep class hierarchies create the fragile base class problem — a change to a base class can silently break distant subclasses depending on undocumented assumptions, because the dependency is implicit in the inheritance chain rather than an explicit interface. Composition flattens that dependency graph into explicit, individually-testable pieces.

React's own migration is the clearest shipped-at-scale proof: class components coupled state, lifecycle, and rendering into one hierarchy, so sharing behavior across unrelated components needed workarounds (HOCs, render props) specifically to route around single inheritance. Hooks replaced this with plain-function composition — no hierarchy at all.

Inheritance-based sharing

class WithSubscription extends React.Component {
  // HOC wraps a component to inject
  // a shared behavior — workaround for
  // single inheritance, not composition
}

Composition-based sharing

function useDataSubscription(source) {
  // a plain function — composes freely
  // with any other hook, no hierarchy
  const [data, setData] = useState(null);
  useEffect(() => { /* subscribe */ }, [source]);
  return data;
}

This isn't "inheritance is bad" — shallow, well-understood hierarchies are fine. Inheritance depth should track how stable the shared behavior actually is; composition is the safer default when extension points aren't fully known in advance.

7. this: Dynamic Dispatch vs. Lexical Capture

this inside a method isn't decided by where the method was defined — it's decided by how it's called. Extract a method from its instance (const fn = obj.method; fn()) and you're calling it a completely different way, so it gets a completely different this.

class Button {
  label = 'Click';
  handleClick = () => { return `Lexical: ${this.label}`; };  // arrow field — safe to extract
  handleHover() { return `Dynamic: ${this.label}`; }          // normal method — unsafe to extract
}

⚠️ Common Pitfalls

✕ "class is a different inheritance mechanism"

There's no separate class engine — it's the same prototype chain. Know the specific behavioral additions (TDZ, new enforcement, non-enumerable methods, super binding) instead of treating it as "the same, but nicer."

✕ Deep class hierarchies (3+ levels) for reuse

Each level is an implicit dependency on the base class's undocumented assumptions. Default to composition past one or two levels.

✕ Extracting a method without handling this

const handler = instance.method; handler() silently loses the dynamic binding — a frequent source of "cannot read property of undefined" bugs in callbacks.

✕ Ignoring shape consistency in hot paths

Properties added conditionally, in varying order, cause hidden-class transitions — real cost in render loops and large data transforms, not a premature optimization.

✕ Composing mixins without handling name collisions

Object.assign(target, mixinA, mixinB) silently lets a later mixin overwrite an earlier same-named method, with no warning.
