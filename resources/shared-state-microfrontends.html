Sharing State Across Micro-Frontends 🔗

Once an app splits into independently-deployed micro-frontends, some state still has to flow between them — a cart, a logged-in user, a checkout session. This is a lookup-and-implementation reference for the mechanisms that actually get used: event bus, federated Redux store, and lighter-weight alternatives.

1. Why this is a different problem

The state taxonomy (server/client/URL/form/persisted state) assumes one app. Splitting into micro-frontends adds a new axis entirely: does the piece of state that needs sharing even live in the same JS realm? That single question determines which of the options below are on the table at all.

Module Federation and single-spa apps share one JS realm — a store instance created in one app is a real, live object another app can import and subscribe to. Iframes never share a realm, no matter how the state is structured — the only channel is postMessage. Get this wrong first and everything downstream (which pattern to reach for) follows automatically.

See also: Micro-frontend architecture for how iframes, single-spa, and Module Federation isolate (or don't isolate) the JS realm in the first place.

2. Event bus (pub-sub over CustomEvent / postMessage)

The lowest-coupling option: apps publish and subscribe to named events on a shared target, instead of sharing a state object directly. Neither app needs to know anything about the other's internal store shape — only the event name and payload contract.

// shared/eventBus.ts — a tiny typed wrapper around EventTarget
const bus = new EventTarget();

export function publish<T>(type: string, detail: T) {
  bus.dispatchEvent(new CustomEvent(type, { detail }));
}

export function subscribe<T>(type: string, handler: (detail: T) => void) {
  const listener = (e: Event) => handler((e as CustomEvent<T>).detail);
  bus.addEventListener(type, listener);
  return () => bus.removeEventListener(type, listener); // unsubscribe
}

// --- Cart MFE, after a successful add-to-cart ---
publish('cart:updated', { itemCount: 3, total: 79.97 });

// --- Checkout MFE, mounted independently ---
const unsubscribe = subscribe<{ itemCount: number; total: number }>(
  'cart:updated',
  ({ itemCount, total }) => updateHeaderBadge(itemCount, total)
);
// call unsubscribe() on unmount to avoid a leaked listener

Across an iframe boundary, swap EventTarget/CustomEvent for postMessage — same pub-sub shape, but the payload now goes through the structured clone algorithm (serializable data only, no functions or DOM references), and the receiving side must validate event.origin:

// Host, sending into an iframe
cartIframe.contentWindow.postMessage(
  { type: 'cart:updated', itemCount: 3, total: 79.97 },
  'https://cart.internal.example.com'
);

// Iframe, receiving
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://trusted-host.example.com') return; // never skip this
  if (event.data?.type === 'cart:updated') {
    updateBadge(event.data.itemCount, event.data.total);
  }
});

Pros

  • Works across framework boundaries — an Angular MFE can talk to a React MFE
  • Works across iframes via postMessage, the one pattern here that does
  • Zero coupling to any specific state library or store shape
  • Easy to add a new subscriber without touching the publisher

Cons

  • No single source of truth — every listener reconstructs its own view
  • Events fired before a listener mounts are simply missed, no replay by default
  • Debugging means tracing event firings across apps, not inspecting one store
  • Payload contract is enforced only by convention (or shared TypeScript types), not the compiler

Best fit: loosely-coupled apps that need occasional cross-app notifications — "the cart changed," "the user logged out" — not apps that need to read and mutate the exact same state.

3. Shared Redux store (federated singleton)

For apps that already share a JS realm, the store itself can be shared the same way React is shared under Module Federation: instantiated once, exposed as a singleton dependency, and every consuming app imports the same live instance rather than creating its own.

// shell/webpack.config.js — the store lives in the shell, exposed to remotes
new ModuleFederationPlugin({
  name: 'shell',
  exposes: { './store': './src/store' },
  shared: {
    redux: { singleton: true },
    'react-redux': { singleton: true },
    react: { singleton: true },
  },
});

// cart/webpack.config.js — consumes the shell's store instead of creating its own
new ModuleFederationPlugin({
  name: 'cart',
  remotes: { shell: 'shell@https://cdn.example.com/shell/remoteEntry.js' },
  shared: {
    redux: { singleton: true },
    'react-redux': { singleton: true },
    react: { singleton: true },
  },
});
// shell/src/store.ts — the single store instance, exposed via Module Federation
import { configureStore, createSlice } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] as CartItem[] },
  reducers: {
    addItem: (state, action) => { state.items.push(action.payload); },
  },
});

export const { addItem } = cartSlice.actions;
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });

// --- Cart MFE — dispatches into the shell's store, not a local copy ---
import { useDispatch } from 'react-redux';
import { addItem } from 'shell/store';

const dispatch = useDispatch(); // still needs shell's <Provider store={store}> wrapping the tree
dispatch(addItem({ sku: 'ABC123', qty: 1 }));

// --- Checkout MFE — reads the same live state, no props/events needed ---
import { useSelector } from 'react-redux';
const items = useSelector((state) => state.cart.items);
The real risk: this inherits Module Federation's singleton-governance problem, one layer up. If the shell bumps its Redux (or React) version and a remote's requiredVersion range stops overlapping, the shared scope can't satisfy the singleton and falls back to an eager duplicate load — the remote silently gets its own store instance instead of the shell's. Dispatches into that duplicate store never reach the shell's subscribers, and reads from it never see the shell's writes — the exact same failure shape as the classic "Invalid Hook Call" bug from a mismatched React version, just manifesting as state that silently stops syncing instead of a thrown error. The mitigation is identical too: contract tests in CI checking a remote's shared ranges against the currently-deployed shell, and pinning consumers to a known-compatible shell version rather than always resolving "latest."

Pros

  • Genuine single source of truth — one store, not N synchronized copies
  • Redux DevTools time-travel debugging works across the whole composed app
  • Standard Redux ecosystem (middleware, selectors, RTK Query) applies uniformly
  • No missed-event problem — a late-mounting consumer just reads current state

Cons

  • Requires a shared JS realm — never works across iframes
  • Every consumer is coupled to the shell's exact Redux/React version
  • A version mismatch fails silently (duplicate store), not loudly
  • Reintroduces tight coupling between teams the micro-frontend split was meant to reduce

Best fit: tightly-integrated apps that genuinely need to read and write the same state in real time — Cart and Checkout sharing one checkout-session — where the coupling cost is worth paying.

4. Other popular approaches

Shared external store — Zustand or useSyncExternalStore

A lighter-weight singleton than Redux, exposed the same way via Module Federation's shared scope. Same realm-sharing requirement and the same version-governance risk as a shared Redux store, with a smaller API surface and less boilerplate.

// shell/src/cartStore.ts — exposed via Module Federation, same as the Redux store above
import { create } from 'zustand';

export const useCartStore = create<{ items: CartItem[]; addItem: (i: CartItem) => void }>(
  (set) => ({
    items: [],
    addItem: (item) => set((state) => ({ items: [...state.items, item] })),
  })
);

// Any consuming MFE, sharing the exact same store instance:
import { useCartStore } from 'shell/cartStore';
const items = useCartStore((s) => s.items);

BroadcastChannel

A browser API purpose-built for cross-context messaging. Unlike a shared store, it works across iframes and separate browsing contexts without needing a shared realm — good fit for infrequent, coarse-grained sync rather than high-frequency UI state.

// Cart MFE
const channel = new BroadcastChannel('cart-sync');
channel.postMessage({ itemCount: 3, total: 79.97 });

// Checkout MFE — even in a different tab or iframe
const channel = new BroadcastChannel('cart-sync');
channel.onmessage = (event) => updateHeaderBadge(event.data.itemCount, event.data.total);

URL or localStorage as the source of truth

For state simple enough to serialize — a selected filter, an auth token — skip synchronization entirely. Each MFE reads and writes the same URL param or storage key directly, so there's no "sync" step to get wrong.

// Any MFE — auth token as the shared source of truth, no messaging needed
const token = localStorage.getItem('auth_token');

// Every open tab is notified automatically when another tab changes it
window.addEventListener('storage', (event) => {
  if (event.key === 'auth_token' && event.newValue === null) {
    redirectToLogin(); // another tab logged out
  }
});

6. Common pitfalls

✕ Reaching for a shared Redux store by default

It recreates Module Federation's singleton-governance problem for your state layer, not just your framework — every team now has to coordinate a version bump. Start with the event bus or BroadcastChannel unless the apps genuinely need to read and mutate the exact same state in real time.

✕ Assuming a shared store works across an iframe boundary

It structurally can't — each iframe has its own JS realm, so "importing" a store from the host just creates a second, disconnected instance. If the isolation is an iframe, the only channel is postMessage, full stop.

✕ No unsubscribe path on the event bus

A subscriber that never calls its unsubscribe function on unmount leaks a listener every time that MFE remounts — the same uncleaned-listener leak pattern that shows up in the memory leak debugging playground, just at the cross-app boundary instead of within one component.

✕ Skipping event.origin validation on postMessage

Without it, any window that can obtain a reference to yours can forge state-sync messages. Always check event.origin against an explicit allow-list before trusting event.data.
