1. The Pipeline, End to End

Every visible pixel is the output of five stages. The engine doesn't run all five on every change — which stages actually re-run is the mental model this whole page exists to make visible.

On first load every stage runs, in order, once. That's the baseline. Everything after this section is about what happens on the second change — a click, a scroll, a resize — where the engine tries to do as little of this as possible. Click the button — the strip above and the matching boxes in the diagram below will highlight in sync as each stage runs.

2. Cost Inspector — Same Element, Three Different Prices

Changing margin-left, background-color, and transform all "look like" a style change from the code you'd write — but they force completely different amounts of work.

How to read this: Layout and Composite move the same elements the same 18px to the right — click them back to back and watch it's the identical visual move. Layout gets there via margin-left (forces the browser to recompute geometry); Composite gets there via transform (compositor-only, geometry untouched). Paint is deliberately different: it only changes color, nothing moves, because color doesn't affect geometry at all. Each click reports how long that change kept the main thread busy — Layout will show a real, non-trivial number; Paint and Composite will hover near zero, which is the entire point: the browser is free to do that work later, off the critical path, so your script barely notices it happened.

3. Layout Thrashing Race — Interleaved vs Batched

el.offsetWidth right after a write forces the browser to flush layout synchronously, on the spot. Do that in a loop and an O(1) operation becomes O(n) forced layouts. Same 400 elements, same total work, two different access patterns.

Batched

Both runs mutate the same 400 elements. The naive run forces up to 400 synchronous layout flushes; the batched run forces roughly one. Numbers will vary by machine — the ratio is the point, and you can verify it independently in DevTools' Performance panel (look for purple "Layout" blocks stacked inside the naive run).

4. Does It Keep Animating When JS Blocks the Main Thread?

Two boxes, same visual motion, two different CSS properties driving it. Click the block button and watch which one keeps moving.

🟧 top racer: animates left (needs Layout every frame) 🟦 bottom racer: animates transform (compositor-only)
HOVER ME

While the thread is blocked, this box won't respond to hover either — same root cause as the freeze in whichever racer stops. In Chromium-based browsers, the transform racer is expected to keep sliding: it's a compositor-thread animation, running independently of the main thread JS is blocking. The left racer visibly stalls because it needs the main thread's Style/Layout/Paint steps every frame.

5. content-visibility: auto — Skipping Off-Screen Work Entirely

6,000 rows, rendered into a 260px-tall scroll box — so almost all of them start off-screen. One version renders normally; the other tells the browser it's allowed to skip layout and paint for rows it can't see yet.

Forced layout time: —

This measures how long a forced synchronous layout takes right after inserting the rows (the same technique DevTools' own "Layout" cost is measured with) — not "time to next paint," which on a fast machine is dominated by compositor/vsync scheduling noise that has nothing to do with the actual work being skipped. If the numbers look close or inverted, click each button 2–3 times in a row — the first content-visibility run can include one-time setup cost that later runs don't pay again.

6. Summary Table

Change triggersExample propertiesWhat runs
Layout + Paint + Composite width, height, top/left, font-size, padding, display Full geometry recompute → repaint → recomposite. The expensive path.
Paint + Composite only background-color, color, box-shadow, border-radius, visibility Geometry unchanged; pixels redrawn.
Composite only transform, opacity (layer-promoted element) No main-thread work past the first frame — GPU re-blends existing textures.

Everything above is a live version of this table. If you take one thing away: before animating a property, ask which row it's in — not whether it "looks cheap" in the code.
