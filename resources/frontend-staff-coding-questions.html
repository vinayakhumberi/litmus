Question 1: Implement debounce

Write a debounce(fn, delay) function with the following behavior:

  1. Standard debounce: only invoke fn after delay ms have passed since the last call.
  2. Support a cancel() method on the returned function to cancel any pending invocation.
  3. Support an immediate option — if true, invoke fn on the leading edge instead of trailing.
  4. Preserve this context and arguments correctly when fn is finally invoked.
function debounce(fn, delay, immediate = false) {
  // your implementation
}

// Usage:
const debounced = debounce(() => console.log('called'), 300);
debounced();
debounced.cancel();

What this tests: closures, timer management, and correctly implementing two related-but-distinct modes (leading vs. trailing edge) without duplicating logic.

Reveal Solution 
function debounce(fn, delay, immediate = false) {
  let timer = null;

  function debounced(...args) {
    const callNow = immediate && timer === null;

    clearTimeout(timer);

    timer = setTimeout(() => {
      timer = null;
      if (!immediate) {
        fn.apply(this, args);
      }
    }, delay);

    if (callNow) {
      fn.apply(this, args);
    }
  }

  debounced.cancel = function () {
    clearTimeout(timer);
    timer = null;
  };

  return debounced;
}

Why it works: a single timer variable tracks whether a debounce window is currently active. In immediate mode, callNow is only true on the first call of a fresh window (timer === null); the timer started afterward exists purely to reset that window once it fully elapses, not to fire fn again. In trailing mode, the setTimeout callback itself does the firing. cancel() clears the pending timer and resets it to null so a subsequent call is treated as fresh.

Question 2: Implement a memoization function with cache invalidation

Write a memoize(fn, options) function that:

  1. Caches results based on the arguments passed (assume arguments are JSON-serializable primitives/objects).
  2. Supports a maxSize option — when the cache exceeds maxSize entries, evict the least recently used (LRU) entry.
  3. Supports a ttl option (milliseconds) — cached entries expire after ttl ms and get recomputed on next access.
  4. Exposes a .clear() method on the returned function to wipe the entire cache.
function memoize(fn, options = {}) {
  // your implementation
}

// Usage:
const expensiveCalc = memoize((a, b) => {
  console.log('computing...');
  return a + b;
}, { maxSize: 100, ttl: 5000 });

expensiveCalc(1, 2); // computing... 3
expensiveCalc(1, 2); // 3 (cached)

What this tests: cache key design, LRU eviction (data structure choice matters — O(1) access + reordering), and TTL bookkeeping.

Reveal Solution 
function memoize(fn, options = {}) {
  const { maxSize = Infinity, ttl = Infinity } = options;
  const cache = new Map(); // key -> { value, expiresAt }

  function memoized(...args) {
    const key = JSON.stringify(args);
    const now = Date.now();

    if (cache.has(key)) {
      const entry = cache.get(key);

      if (entry.expiresAt > now) {
        // LRU bump: delete + re-set moves this key to the "most recent" end
        cache.delete(key);
        cache.set(key, entry);
        return entry.value;
      } else {
        cache.delete(key); // expired, evict it
      }
    }

    const value = fn.apply(this, args);
    const expiresAt = ttl === Infinity ? Infinity : now + ttl;
    cache.set(key, { value, expiresAt });

    if (cache.size > maxSize) {
      const oldestKey = cache.keys().next().value;
      cache.delete(oldestKey);
    }

    return value;
  }

  memoized.clear = function () {
    cache.clear();
  };

  return memoized;
}

Why it works: Map preserves insertion order, which is exploited for O(1) LRU tracking — re-inserting a key on access moves it to the "newest" end, so the first key in iteration order is always the least recently used. TTL is stored per-entry since different calls are cached at different times.

Known limitation worth stating out loud: JSON.stringify as a key breaks down for undefined arguments and is sensitive to object key ordering ({a:1,b:2} vs {b:2,a:1} stringify differently despite being logically equal).

Question 3: Implement a simple Event Emitter

Build an EventEmitter class with:

class EventEmitter {
  on(event, callback) {}
  off(event, callback) {}
  emit(event, ...args) {}
  once(event, callback) {}
}

Requirements:

  1. on(event, callback) registers a listener; multiple listeners for the same event should all fire, in registration order.
  2. off(event, callback) removes a specific listener (not all listeners for that event).
  3. emit(event, ...args) calls all registered listeners for that event with the given args.
  4. once(event, callback) registers a listener that fires exactly once, then auto-removes itself.
  5. Tricky part: if a listener calls off() on another listener for the same event, from within its own callback during an active emit(), the emit should still behave correctly — no skipped listeners, no crashes.

What this tests: correct data structure choice, mid-iteration mutation safety, and clean API design (avoiding duplicated bookkeeping for once vs. regular listeners).

Reveal Solution 
class EventEmitter {
  listeners = new Map();
  oncelist = new Map();

  on(event, callback) {
    if (!this.listeners.get(event)) {
      this.listeners.set(event, []);
    }
    this.listeners.get(event).push(callback);
  }

  once(event, callback) {
    if (!this.listeners.get(event)) {
      this.listeners.set(event, []);
    }
    this.listeners.get(event).push(callback);
    this.oncelist.set(callback, true);
  }

  off(event, callback) {
    const cbs = this.listeners.get(event) || [];
    const index = cbs.indexOf(callback);
    if (index > -1) {
      cbs.splice(index, 1);
    }
    if (this.oncelist.get(callback)) {
      this.oncelist.delete(callback);
    }
  }

  emit(event, ...args) {
    const cbs = this.listeners.get(event) || [];
    const snapshot = [...cbs]; // immune to mutation during iteration
    for (let i = 0; i < snapshot.length; i++) {
      snapshot[i].apply(this, args);
      if (this.oncelist.get(snapshot[i])) {
        this.off(event, snapshot[i]);
      }
    }
  }
}

Why it works: a single array per event preserves true registration order (no separate once list that could fire out of order relative to on listeners). emit iterates a snapshot of the array, so removals triggered mid-emit (by off, or by a once listener auto-removing itself) never shift indices out from under the active loop.

Question 4: Fix a race condition in a search component

Here's a typical "search-as-you-type" component. It has a subtle but classic bug.

function SearchResults({ query }) {
  const [results, setResults] = useState([]);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    setLoading(true);
    fetch(`/api/search?q=${query}`)
      .then(res => res.json())
      .then(data => {
        setResults(data);
        setLoading(false);
      });
  }, [query]);

  if (loading) return <p>Loading...</p>;
  return (
    <ul>
      {results.map(item => <li key={item.id}>{item.name}</li>)}
    </ul>
  );
}

Your task:

  1. Identify the bug — describe when it manifests and the exact mechanism (what two requests, in what order, cause what wrong outcome).
  2. Fix it using two different techniques — first with a manual cleanup-flag/ignore pattern (no AbortController), then rewrite it using AbortController to actually cancel the in-flight request.
  3. Bonus: what changes if query updates very rapidly (e.g., every keystroke, no debounce upstream)? Does your fix alone make this efficient, or just correct? What would you add?

What this tests: understanding of useEffect cleanup semantics, the difference between "ignoring a stale result" and "cancelling a request," and recognizing that correctness and efficiency are separate concerns.

Reveal Solution

The bug, precisely: if query changes from "a" to "ab" quickly, two requests are in flight. Response order is not guaranteed to match request order — if the "a" response arrives after the "ab" response (e.g. due to server timing or network jitter), its .then() fires last and calls setResults(dataForA), overwriting the correct "ab" results with stale "a" results.

Fix A — manual ignore-flag pattern:

useEffect(() => {
  let ignore = false;
  setLoading(true);

  fetch(`/api/search?q=${query}`)
    .then(res => res.json())
    .then(data => {
      if (!ignore) {
        setResults(data);
        setLoading(false);
      }
    });

  return () => {
    ignore = true;
  };
}, [query]);

Each effect run has its own private ignore closure. React runs the previous effect's cleanup before the new effect starts, flipping the old ignore to true — so when the stale request resolves, its result is discarded. Note: this doesn't cancel the network request itself, only its effect on state.

Fix B — AbortController (also cancels the request):

useEffect(() => {
  const controller = new AbortController();
  setLoading(true);

  fetch(`/api/search?q=${query}`, { signal: controller.signal })
    .then(res => res.json())
    .then(data => {
      setResults(data);
      setLoading(false);
    })
    .catch(err => {
      if (err.name !== 'AbortError') throw err;
    });

  return () => {
    controller.abort();
  };
}, [query]);

Bonus — rapid keystrokes: cancellation makes this correct, not efficient. It still fires (and immediately aborts) a request on every keystroke. The efficiency fix is a debounced query value upstream (e.g., useDebouncedValue(query, 300)) feeding into this effect — debounce and cancellation solve different problems and are typically used together.

Question 5: Implement Promise.all from scratch

Write your own version of Promise.all:

function promiseAll(promises) {
  // your implementation — must return a Promise
}

Requirements:

  1. Resolves with an array of results, in the same order as the input array — even though promises may resolve out of order.
  2. Rejects immediately with the first rejection reason encountered (fail-fast), even if other promises are still pending.
  3. Handle an empty array input correctly (promiseAll([]) should resolve immediately with []).
  4. Handle non-promise values in the array (e.g. promiseAll([1, Promise.resolve(2), 3]) should treat plain values as already-resolved).

What this tests: understanding of the Promise executor, closures for tracking async completion count, and edge cases most people forget (empty array, non-promise values, preserving the original rejection reason unmodified).

Reveal Solution 
function promiseAll(promises = []) {
  return new Promise((resolve, reject) => {
    if (promises.length === 0) {
      resolve([]);
      return;
    }

    const outputData = [];
    let completed = 0;

    promises.forEach((promise, index) => {
      Promise.resolve(promise).then((data) => {
        outputData[index] = data;
        completed++;
        if (completed === promises.length) {
          resolve(outputData);
        }
      }).catch((error) => {
        reject(error);
      });
    });
  });
}

Why it works:

Order preserved: writing to outputData[index] directly (not .push) means results land in input order regardless of resolution order.

Fail-fast: reject(error) fires immediately on the first rejection, independent of other pending promises. A Promise can only settle once, so any later resolve/reject calls are harmless no-ops.

Empty array: handled with an explicit early check before iterating — without it, the returned promise would hang forever.

Non-promise values: Promise.resolve(promise) is idempotent on real promises and wraps plain values into already-resolved promises, so .then works uniformly on every element.

Original error preserved: reject(error) passes the rejection reason through unmodified — don't wrap it in a new generic Error, which would destroy properties/stack traces callers may depend on.

Question 6: Implement a mini state store (Redux-lite)

Build a simple observable store:

function createStore(reducer, initialState) {
  // your implementation
}

// Usage:
const reducer = (state, action) => {
  switch (action.type) {
    case 'INCREMENT': return { ...state, count: state.count + 1 };
    case 'DECREMENT': return { ...state, count: state.count - 1 };
    default: return state;
  }
};

const store = createStore(reducer, { count: 0 });

const unsubscribe = store.subscribe((state) => console.log('state changed:', state));

store.dispatch({ type: 'INCREMENT' }); // logs: state changed: { count: 1 }
store.getState(); // { count: 1 }

unsubscribe();
store.dispatch({ type: 'INCREMENT' }); // no log — listener removed

Requirements:

  1. getState() returns the current state (should be treated as read-only externally — think about what a reasonable level of protection looks like, since full immutability is hard to guarantee in JS).
  2. dispatch(action) runs the reducer, updates internal state, and notifies all subscribed listeners with the new state.
  3. subscribe(listener) registers a listener and returns an unsubscribe function (the returned closure itself should do it, not a separate method).
  4. Multiple listeners should all fire, in registration order.
  5. Tricky part: if a listener calls dispatch() again from within itself (a nested dispatch, triggered by a state change), decide on an explicit policy (allow / queue / throw) and enforce it.

What this tests: the same subscribe/unsubscribe/mid-iteration patterns as the EventEmitter question, plus reducer purity assumptions and re-entrancy policy.

Reveal Solution 
function createStore(reducer, initialState) {
  let store = initialState;
  let subscribers = [];
  let isDispatching = false;

  const dispatch = (action) => {
    if (isDispatching) {
      throw new Error('Cannot dispatch while a dispatch is already in progress.');
    }
    isDispatching = true;
    try {
      store = reducer(store, action);
    } finally {
      isDispatching = false;
    }
    const snapshot = [...subscribers];
    snapshot.forEach((subscriber) => subscriber(store));
  };

  const getState = () => ({ ...store });

  const subscribe = (fn) => {
    subscribers.push(fn);
    return () => {
      subscribers = subscribers.filter(sub => sub !== fn);
    };
  };

  return { subscribe, getState, dispatch };
}

Why it works:

Read-only protection: getState() returns a shallow copy, so mutating the returned object doesn't corrupt internal state. (Known limitation: only shallow — nested objects are still mutable by reference. Object.freeze(store) is a common alternative.)

Subscriber storage: a plain array, not an object keyed by stringified function — using fn.toString() as an object key risks silent collisions between structurally identical listener functions.

Mid-dispatch mutation safety: dispatch snapshots subscribers into a new array before notifying, so a listener calling unsubscribe() on another listener mid-dispatch can't skip anyone.

Re-entrancy policy: isDispatching explicitly guards against a reducer triggering another dispatch while one is already computing, throwing rather than silently allowing undefined behavior — matching real Redux's stance ("Reducers may not dispatch actions").

Design trade-off worth noting: this guard is scoped narrowly around reducer execution only, so a listener calling dispatch after being notified (not during reducer execution) is still allowed — a deliberate choice, since forbidding that entirely would block legitimate "dispatch a follow-up action after a state change" patterns. Wrapping the guard around the whole dispatch (including listener notification) is a stricter alternative worth naming explicitly as a trade-off in an interview.
