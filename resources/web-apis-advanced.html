1. Where Each API Sits in the Frame Lifecycle

All four of these APIs exist to solve one problem: doing work without fighting the browser's render pipeline. The most important thing to internalize isn't the method names — it's exactly when each callback fires relative to the event loop.

2. requestAnimationFrame — Coalescing High-Frequency Events

A mousemove event can fire far more often than the screen can actually redraw. Writing to the DOM on every single event wastes work on frames the user will never see — and if each write is even slightly expensive, it compounds into visible jank.

3. requestIdleCallback — Genuinely Low-Priority Work

Some work matters, but not urgently — analytics batching, speculative prefetch, cache warming. requestIdleCallback only runs it when the main thread truly has nothing more important to do, using a deadline object that tells you how much idle time is actually left.

4. IntersectionObserver — Visibility Without Forcing Layout

A scroll listener calling getBoundingClientRect() forces a synchronous layout recalculation on every call. IntersectionObserver reports visibility asynchronously, using layout data the browser is already computing — without you ever forcing extra work.

Scroll a few times with the naive comparison enabled — its counter climbs fast (every row, every scroll tick, forcing layout each time), while the IntersectionObserver counter only ticks when a row actually crosses the visibility threshold.

5. MutationObserver — Microtask-Batched, Not Per-Mutation

The old Mutation Events fired synchronously, once per DOM change — a performance disaster at scale, which is why they were deprecated. MutationObserver batches everything since the last microtask checkpoint into a single callback.

6. Summary Table

API Fires as Guaranteed? Forces layout? Typical use case
requestAnimationFrame Once per frame, pre-render Yes, if tab is visible No, if you avoid interleaved reads Animations, visual DOM sync, FLIP transitions
requestIdleCallback During idle periods only No — timeout is the only guarantee No Low-priority background work, analytics batching
IntersectionObserver Async, browser-batched Eventually, timing not in your control No — this is its entire purpose Lazy loading, infinite scroll, viewability tracking
MutationObserver As a microtask, batched Yes — deterministic per spec No Detecting third-party/uncontrolled DOM changes

Takeaway

Every counter above is telling the same story: the naive approach does more work, more often, on the main thread, while the purpose-built API does less work, batched, at the right moment. That's the whole argument for reaching for these four APIs by default instead of scroll listeners, raw timers, and synchronous mutation handling.
