1. React Profiler Basics — What You're Actually Looking At

The Profiler doesn't record every render — it records commits. A commit is the point where React actually flushes a completed render to the DOM. Every commit you record shows up as one bar in the commit picker at the top of the real Profiler tab; click a bar to inspect just that commit.

Inside a selected commit, there are two ways to view which components rendered:

ViewWhat it shows
FlamegraphThe component tree for this one commit. Bar width = how much of this commit's total time that component's subtree accounted for. Color = relative duration (yellow/orange = slower, blue/green = faster). A component that bailed out via React.memo (or PureComponent) with no changed context either is commonly missing from the chart entirely for that commit — not grayed out, just absent, since React never had to visit it. (Older guidance describes these as gray bars; in current extension versions they're simply not drawn — don't be surprised when a bailed-out sibling doesn't appear at all next to one that did render.)
RankedThe same commit's components sorted by render duration, longest first, flattened out of the tree shape. Components that didn't render aren't shown at all. Use this when you just want "what's slow," not "where does it sit in the tree."

Every profiled component reports two numbers, and the gap between them is often the whole story:

TermMeaning
actualDurationHow long this render actually took, including any time saved by children bailing out via memoization.
baseDurationAn estimate of how long the subtree would take to render with no memoization at all — React's own "worst case" baseline.
If actualDuration is close to baseDuration on a component wrapped in React.memo, memoization isn't actually helping there — either it's re-rendering every time anyway (the scenarios below show why), or the subtree is cheap enough that memoization wouldn't matter either way.

Two more things worth knowing before you record anything: DevTools has a per-component "why did this render" panel (props/state/hooks/context changed, or parent re-rendered) — it must be turned on first via the gear icon in the Profiler tab's settings, before you record. And separately, "Highlight updates when components render" (also in settings) is an always-on visual overlay, unrelated to recording — it flashes a colored border around any DOM element that just re-rendered, live, as you use the app. It's the Profiler-panel equivalent of a 10-second smoke test, the same role Performance Monitor plays for memory in the companion memory-leak resource.

2. How to Capture a Profile (Real Extension)

Everything below this section runs a genuine, live React 18 app you can profile with the real tool. If you don't have it yet, install the React Developer Tools browser extension first.

  1. Open your browser's DevTools on this page (F12 / Cmd+Opt+I) and switch to the ⚛️ Profiler tab (a new tab the extension adds, separate from Chrome's own Memory/Performance tabs).
  2. Click the gear icon in the Profiler tab's toolbar → check "Record why each component rendered while profiling". Do this now — it can't be turned on retroactively for a recording you already made.
  3. Click the blue record circle (top-left of the Profiler tab) to start recording.
  4. Go interact with a scenario below (click its buttons a few times).
  5. Click the record circle again to stop. A row of commit bars appears at the top — each one is a single commit captured while you were recording.
  6. Click through the commit bars one at a time. For each, look at the Flamegraph (or switch to Ranked via the dropdown next to the commit bars), and click on any individual component's bar to open the "why did this render" panel for it on the right.

3. Scenario: Breaking React.memo — Two Different Ways

40 ProductRow components, each wrapped in React.memo. A "tick" button simulates something unrelated re-rendering the shared parent — think of it as a clock in the header, or any sibling state change that has nothing to do with the product list. Both bugs below are the same root cause — a prop that's a new object/function reference every render — showing up in two shapes people don't always recognize as the same bug.

// BUG A: new function reference every render, even for unrelated ticks
const onSelect = (id) => selectProduct(id);
// FIX A: stable reference across renders
const onSelect = useCallback((id) => selectProduct(id), []);

// BUG B: new object literal every render, even with the callback fixed
<ProductRow style={{ opacity: 1 }} />
// FIX B: hoist it - it never actually depends on props/state
const ROW_STYLE = { opacity: 1 };
<ProductRow style={ROW_STYLE} />

The panel below is built on React's real, public <Profiler> API — the same instrumentation the actual DevTools extension uses internally — wrapping the list and every individual row. Nothing here is a mockup; the durations and render/bail-out status are genuinely captured from your browser as you click.

A. Confirm the callback bug (fix OFF, inline style OFF)
  1. Make sure Apply the fix (wrap onSelect in useCallback) and Pass an inline style object are both unchecked, and Simulate ~1.2ms of render work per row is checked.
  2. Click Trigger unrelated re-render (tick) two or three times.
  3. Look for: "Rows re-rendered" reading 40 / 40 every single click, and every bar in the flame chart below colored (not gray). Hover any bar — the tooltip reads "re-rendered: onSelect", confirming it's the callback reference changing, not product data.
  4. Optional, in the real extension (see section 2 above): record the same click, open the Flamegraph for that commit — you'll see the identical 40 colored ProductRow bars, and clicking one shows "why did this render: props changed (onSelect)" in the side panel.
B. Confirm the callback fix
  1. Check Apply the fix (leave inline style unchecked).
  2. Click Trigger unrelated re-render (tick) a few more times.
  3. Compare: "Rows re-rendered" should now read 0 / 40 — every row bailed out via React.memo, and every bar is gray with the tooltip "bailed out (memo)".

🔎 Deduction: what the evidence means, and where to look in real code

What it means: a memoized component that re-renders on every parent update, where the "why did this render" panel names a function prop as the changed value, means the parent is defining that function inline in its render body — React.memo is doing its job correctly, it's just being handed a prop that's never equal to itself twice.

Where to look in your own codebase:

  • Grep for components wrapped in memo(, then check every prop their parent passes for an inline arrow function or bound method: 
    grep -rn "memo(" src/
  • In the parent, look for callback props defined as onClick={() => doThing(id)} or onClick={this.doThing.bind(this)} directly in JSX — both allocate a new function every render. The fix is useCallback (function components) or binding once in the constructor (class components).
  • Turn on ESLint's react/jsx-no-bind rule (from eslint-plugin-react) — it flags exactly this pattern at lint time, before it ever reaches the Profiler.
  • If the "why did this render" panel isn't available, a quick manual check: pass a custom second argument to memo(Component, (prev, next) => ...) and console.log which specific prop fails Object.is — this pinpoints the exact prop without needing the extension at all.

Scenario B: Inline Object/Array Literal Prop Defeats memo Too

Fixing the callback isn't the whole fix if another prop has the same problem. The checkbox below controls whether the same list also receives a style object built fresh every render (style={{ opacity: 1 }}) versus a single hoisted constant — same values, but only one of the two is referentially stable.

A. Confirm the inline-object bug (fix ON for callback, inline style ON)
  1. Check Apply the fix (from Scenario A above) so the callback is no longer the variable — then check Pass an inline style object too.
  2. Click Trigger unrelated re-render (tick) a few times.
  3. Look for: "Rows re-rendered" back up to 40 / 40, even though the callback fix is still applied — hover a bar and the tooltip now reads "re-rendered: rowStyle" instead of "onSelect". Same symptom, different prop, proving fixing one unstable prop doesn't help if another one is still unstable.
B. Confirm the fix (hoisted style object)
  1. Uncheck Pass an inline style object, leaving the callback fix checked.
  2. Click Trigger unrelated re-render (tick) again.
  3. Compare: "Rows re-rendered" drops back to 0 / 40 — with both props now stable, every row bails out.

🔎 Deduction: what the evidence means, and where to look in real code

What it means: if you've already memoized a callback and a component still re-renders every time, "why did this render" naming a plain object/array prop (not a function) means the same referential-equality problem exists one prop over — style={{ ... }}, data={[...]}, or any object/array literal written directly in JSX is a new reference on every render, full stop.

Where to look in your own codebase:

  • Grep JSX for object/array literals passed as props — the opening ={{ or ={[ is the tell: 
    grep -rn "=\{\{" src/*.jsx src/**/*.jsx 2>/dev/null
  • For each hit feeding into a memo-wrapped component, decide which fix applies: if the value never depends on props/state (like this demo's style), hoist it to a module-level constant outside the component entirely. If it genuinely depends on props/state, wrap it in useMemo(() => ({ ... }), [deps]) instead.
  • Inline array literals for list-shaped props (items={[1,2,3]}) have the identical problem and the identical two fixes.

4. Scenario: Unmemoized Context Value Re-renders Every Consumer

One context wraps three independent, memoized consumer widgets. Every consumer reads from it — but only one of them, ClockWidget, actually needs to update every second. In buggy mode, the Provider's value prop is a fresh object literal every render, so React treats the context value as "changed" for every consumer on every tick — including the two widgets that never asked for that update. This is a different mechanism from React.memo entirely: a component consuming context via useContext re-renders whenever that context's value changes, and React.memo cannot stop it — memoization only blocks re-renders caused by the parent, not ones caused by a context the child subscribes to directly.

// BUG: one context, one object, mixing a fast-changing field with slow ones
<AppContext.Provider value={{ theme, seconds }}>
  {/* ClockWidget, UserPanel, SettingsPanel all read the same context */}

// TEMPTING BUT INCOMPLETE: useMemo doesn't actually fix this
const value = useMemo(() => ({ theme, seconds }), [theme, seconds]);
// `seconds` is still a dependency, so this still recomputes every tick -
// every consumer of this context still re-renders every second, unfixed.

// THE REAL FIX: split into two contexts, one per concern
<ThemeContext.Provider value={theme}>
  <TimeContext.Provider value={seconds}>
    {/* ClockWidget reads TimeContext; UserPanel/SettingsPanel read ThemeContext */}
  </TimeContext.Provider>
</ThemeContext.Provider>
A. Confirm the context bug (fix OFF)
  1. Make sure Split into two contexts (the real fix) is unchecked.
  2. Click Start ticking and let it run for a few seconds.
  3. Look for: all three "renders" counters — ClockWidget, UserPanel, and SettingsPanel — climbing in lockstep, once per second, even though UserPanel and SettingsPanel display nothing that changes every second.
  4. Optional, in the real extension: record a couple of ticks, open the Flamegraph — all three consumer components show as colored (rendered) on every single commit, and clicking SettingsPanel's bar shows "why did this render: context changed" even though neither its props nor its own state changed.
B. Confirm the fix (fix ON)
  1. Check Split into two contexts (the real fix).
  2. Click Reset counters (toggling recreates the widgets, so this gives you a clean comparison), then let it tick for a few more seconds.
  3. Compare: ClockWidget's counter keeps climbing (it's supposed to — it displays the seconds), but UserPanel and SettingsPanel's counters now stay completely flat — they only move if you click Toggle theme, which is the one thing they actually care about.

🔎 Deduction: what the evidence means, and where to look in real code

What it means: multiple unrelated components re-rendering in perfect sync with each other, all tracing back to "context changed" in the why-did-this-render panel rather than to their own props or state, means they all share one context whose value object is being rebuilt on every Provider render — React.memo on the consumers won't save you, because context reads bypass the parent-prop-comparison memo relies on entirely.

Where to look in your own codebase:

  • Grep for every .Provider value= in the app and check whether the value is an inline object literal: 
    grep -rn "\.Provider" src/ | grep "value={"
  • Before reaching for useMemo, check what's actually inside that object first: if any one field changes on a timer, a subscription, or fast user input, wrapping the whole object in useMemo won't help — that field is a dependency, so the memoized value still changes exactly as often as the fastest field does, and every consumer still pays for it. This demo's "fix" isn't useMemo at all; it's splitting seconds and theme into two separate contexts.
  • The tell to search for: one context's value object mixing a field that changes on a timer/subscription/frequent-input with a field that changes rarely (a theme, a feature flag, a logged-in user). That mismatch in change-frequency, bundled into one object, is what forces slow-changing consumers to re-render at the fast field's rate.
  • The fix is always the same shape: give the fast-changing field its own context, so a component that only reads the slow-changing one can subscribe to just that context and never re-render on the fast tick at all.

5. Detection Toolkit: Reading a Real Profiling Session

The three scenarios above tell you exactly which prop or context is at fault because they're instrumented to say so. In a real app, you won't have that ground truth handed to you — here's how to get the same answers out of the real extension on a codebase you don't already know inside out.

Flamegraph vs. Ranked — when to use which

Default to Ranked when you already know a commit felt slow and just want to know what to open first — it sorts every component that rendered by duration, longest at the top, with the tree shape stripped away. Switch to Flamegraph once you have a suspect and need to see where it sits relative to its parents and siblings — specifically, whether a slow child sits under a parent that could have blocked it from rendering at all via memo. Note that a sibling which bailed out (via memo, or by not subscribing to whatever context/state changed) typically isn't drawn at all for that commit rather than shown grayed-out — so "my suspect is the only thing in this row" is itself the signal that everything else correctly bailed out, not proof that nothing else exists in the tree.

"Why did this render" — reading it correctly

Click any component's bar in either view (after turning the setting on, per section 2 above) to open this panel. It reports one of a small set of reasons: props changed (and names which ones), state changed, hooks changed (context read via a hook, or a custom hook's internal state), context changed, or parent re-rendered (no memoization at all on this component, so it renders whenever its parent does regardless of props). That last one is worth specifically checking for: a component with no memoization shows this reason on every single commit, which is expected and not itself a bug — only worth fixing if that component's actualDuration is high enough to matter.

Highlight updates when components render — a smoke test, not a recording

This is a separate toggle (also under the gear icon), and unlike everything else here, it needs no recording at all — turn it on and it stays on, flashing a colored border around any DOM element whose component just rendered, live, the instant it happens. Use it before you ever open the Profiler proper: click around the real app for a few seconds with this on, and anything flashing that has no visible reason to update (a static header, a sidebar you didn't touch) is your first lead on where to record a real profile.

Cross-checking with the Components tab

The Profiler tells you that and why something rendered; the extension's other tab, ⚛️ Components, lets you inspect what it actually received. Select the same component there (search by name in its search box) and look at its current Props/State/Hooks panel on the right — useful for confirming a suspicion from "why did this render" (e.g., it says a prop object changed; the Components panel lets you expand that object and see whether its fields are actually different, or identical-but-a-new-reference, which is precisely the bug Scenario B above reproduces).
