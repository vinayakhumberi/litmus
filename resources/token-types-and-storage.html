Token Types & Storage 🔑

What each kind of token is for, when to reach for it, and where it's actually safe to keep it

Token Types Storage Options Token Flow Which One Do I Need? Security Notes

"Token" gets used loosely to mean a lot of different things — a session ID, a JWT, an API key, a CSRF nonce. They solve different problems and have different rules for where they can safely live. This page treats "type of token" and "storage location" as two separate decisions, because conflating them is where most auth bugs come from.

1. Token Types

TokenDetailsStore inNever store in
Access Token

PurposeProves to an API that the bearer is authorized to call it, scoped to specific permissions. What you attach to Authorization: Bearer <token> headers.

FormatJWT (self-contained claims) or opaque (looked up server-side)

LifetimeShort — minutes to ~1 hour, by design
  • In-memory (JS variable / module state)
  • OS Keychain/Keystore (mobile apps)
  • localStorage
  • sessionStorage
  • URL query params
Refresh Token

PurposeUsed only to obtain a new access token once the old one expires, without forcing the user to log in again. Never sent to resource APIs directly.

FormatOpaque, usually rotated on each use

LifetimeLong — days to months
  • httpOnly, Secure, SameSite cookie
  • OS Keychain/Keystore (mobile apps)
  • localStorage
  • sessionStorage
  • In-memory only — lost on refresh, forces re-login
Session ID

PurposeOpaque reference to server-side session state (user id, permissions, cart, etc.). The server looks it up on every request; the client never sees the actual data.

FormatRandom opaque string, not a JWT

LifetimeMinutes to weeks, server-controlled — revocable instantly since the server owns the record
  • httpOnly, Secure, SameSite cookie
  • localStorage
  • sessionStorage
ID Token (OIDC)

PurposeProves identity ("who the user is") to the client app itself — not for calling APIs. Distinct from an access token, which proves authorization to a resource server.

FormatAlways a JWT, signed by the identity provider

LifetimeShort — consumed once at login, not reused per-request
  • In-memory (JS variable / module state), just long enough to read claims and discard
  • localStorage
  • sessionStorage
  • httpOnly, Secure, SameSite cookie — never send it as if it were an access token
OAuth Token (third-party)

PurposeLets your backend call a third-party provider's API (Google Calendar, GitHub, Slack) on the user's behalf, after they approve it on that provider's consent screen. Not the same thing as the access token your own auth server issues for your own API — this one belongs to the provider.

FormatOpaque or JWT — shape is entirely the third-party provider's choice, not yours

LifetimeProvider-defined, often short-lived with its own provider-issued refresh token
  • Server-side only, attached to the user's account record, encrypted at rest
  • httpOnly, Secure, SameSite cookie
  • In-memory (JS variable / module state)
  • localStorage
  • sessionStorage
CSRF Token

PurposeProves a state-changing request originated from your own page, not a cross-site form/script riding on the user's cookies. Only matters when auth relies on cookies sent automatically by the browser.

FormatRandom nonce, echoed from a cookie/meta tag into a request header or hidden form field

LifetimePer-session or per-form
  • Cookie, but without httpOnly — JS must be able to read it to echo it back
  • httpOnly, Secure, SameSite cookie — JS couldn't read it back to echo it
  • localStorage/sessionStorage as the only defense, without pairing it to SameSite
API Key

PurposeIdentifies the calling application or project, not an end user — server-to-server or third-party integrations (Stripe, Google Maps).

FormatStatic opaque string

LifetimeLong-lived until manually rotated/revoked
  • Server-side secrets manager or environment variable
  • localStorage
  • sessionStorage
  • Client-side bundle/source code, or committed to git
Personal Access Token (PAT)

PurposeA long-lived, manually-issued token a user generates to authenticate scripts/CLIs as themselves, bypassing the interactive login flow (GitHub, GitLab tokens).

FormatStatic opaque string, usually scoped to specific permissions

LifetimeLong-lived, user-revocable
  • OS keychain / credential manager
  • gitignored local config file
  • localStorage
  • sessionStorage
  • Hardcoded in source, or committed to git
One-Time Token

PurposeSingle-use token for email verification, password reset, or magic-link login. Invalid the moment it's used, or after a short expiry.

FormatRandom opaque string, usually embedded in a URL

LifetimeMinutes, single-use
  • Nowhere client-side by design — consumed in a single request and invalidated server-side immediately after
  • localStorage
  • sessionStorage
  • Any persistent client storage that would let it be reused

"OAuth token" isn't really a separate category from Access/Refresh Token above — OAuth is the delegation framework, and it issues access + refresh tokens using the exact same mechanics. The distinction that matters is who issued it: your own auth server (your Access/Refresh Token rows — safe to hand to the client, per the storage rules above) vs. an external provider like Google or GitHub (the OAuth Token row — stays server-side, full stop, since the client has no business holding another company's credential for your app).

2. Where to Store Them

The four realistic options on the client, ranked by what they actually protect against. There's no single "correct" answer — it's a trade-off between XSS exposure and CSRF exposure, and which one your app is more able to defend against.

LocationSurvives refresh?Exposed to XSS?Sent automatically (CSRF risk)?Notes
httpOnly, Secure, SameSite cookie Yes (until expiry) No — JS can't read it at all Yes — browser attaches it to every matching request The standard recommendation for session IDs and refresh tokens. Needs a CSRF token alongside it for state-changing requests, unless SameSite=Strict/Lax covers your case.
In-memory (JS variable / module state) No — lost on tab refresh or close Yes, if an XSS payload runs while it's held — but nothing persists for an attacker to steal later No — you attach it explicitly Best option for short-lived access tokens in an SPA: pair with a refresh flow (silent refresh via httpOnly cookie) so losing it on refresh is invisible to the user.
localStorage Yes (until manually cleared) Yes — any injected script can read it, and it persists for future reuse No — you attach it explicitly Common in practice, but the persistence is exactly what makes an XSS hit worse — a stolen token stays valid and readable long after the payload ran.
sessionStorage Only within the same tab Yes — same exposure as localStorage while the tab is open No — you attach it explicitly Slightly smaller blast radius than localStorage (cleared on tab close, not shared across tabs) but the same fundamental XSS exposure.

Prefer httpOnly cookies for:

  • Session IDs
  • Refresh tokens
  • Anything long-lived, where an XSS-stolen token would do lasting damage

Avoid localStorage/sessionStorage for:

  • Refresh tokens (long-lived + readable by any injected script = worst combination)
  • Anything that grants broad account access on its own

3. Access Token + Refresh Token Flow

        sequenceDiagram
            participant U as Browser (SPA)
            participant A as Auth Server
            participant R as Resource API

            U->>A: Login (credentials)
            A-->>U: Access token (short-lived, in memory) + Refresh token (httpOnly cookie)
            U->>R: API call with Authorization: Bearer access_token
            R-->>U: 200 OK
            Note over U,R: ...time passes, access token expires...
            U->>R: API call with expired access token
            R-->>U: 401 Unauthorized
            U->>A: POST /refresh (refresh token sent automatically via cookie)
            A-->>U: New access token (+ rotated refresh token)
            U->>R: Retry API call with new access token
            R-->>U: 200 OK

The access token never touches disk on the client. The refresh token never gets attached to resource-API calls directly — it only ever talks to the auth server, and only over an httpOnly cookie the page's own JS can't read.

4. Which One Do I Need?

SPA calling your own backend

Short-lived access token held in memory + httpOnly refresh cookie for silent renewal. Add a CSRF token if the refresh endpoint is cookie-authenticated.

Server-rendered app (traditional MVC)

Just a session cookie — httpOnly, Secure, SameSite=Lax. No access/refresh split needed since there's no separate client-side JS holding credentials.

Mobile app calling an API

Access + refresh token pair, both stored in the OS-level secure storage (Keychain/Keystore) — cookies don't apply the same way outside a browser, and the platform's secure storage already solves the "readable by other apps" problem.

Server-to-server / machine-to-machine

API key or a client-credentials-flow access token — there's no end user, so session/ID tokens don't apply. Store in a secrets manager or environment variable, never in source control.

CLI or script authenticating as a specific user

Personal Access Token, scoped as narrowly as the task allows, stored in an OS keychain or a gitignored config file — never hardcoded.

5. Security Notes

Why access tokens are short-lived

A short expiry limits the damage window if one leaks — an attacker gets minutes, not months. The refresh token (which never leaves the httpOnly cookie jar) is what makes that survivable for the user, since they don't have to re-login every few minutes.

Rotate refresh tokens on use

Issuing a new refresh token every time one is redeemed, and invalidating the old one, means a stolen-but-unused refresh token becomes detectable — if both the attacker and the real user try to use it, the second use fails and the server can revoke the whole chain.

JWT ≠ automatically secure

A JWT is just a signed, base64-encoded payload — anyone can decode and read the claims (never put secrets in one). Signing proves it wasn't tampered with; it does nothing to keep it confidential or revocable before its expiry, unless you maintain a server-side denylist.

CSRF tokens only matter with cookie auth

If your API only accepts a bearer token you attach manually in JS, there's no CSRF exposure — a cross-site request can't make your JS run to attach it. CSRF only becomes relevant the moment auth rides on a cookie the browser sends automatically.
